# Prepped 기술 명세

상태: v0.1.0 기준
마지막 갱신: 2026-08-16

## 1. 제품 목적

Prepped는 시니어 사용자가 키오스크에서 겪는 가장 큰 병목을 결제 직전까지의 메뉴 탐색·선택 과정으로 가정한다. 사용자는 휴대폰에서 자주 먹는 메뉴 조합을 한 번 저장하고, 키오스크에서 개인 QR 하나를 스캔해 선택 단계를 줄인다.

v0.1.0은 실제 매장 카탈로그 조회와 원문 QR 기반 키오스크 메뉴 복원을 연결한다. 주문 생성·결제는 별도 백엔드 경계이며, 카탈로그 가격과 이미지 출처가 실제 POS 판매 조건을 보증하지 않는다.

## 2. 사용자 표면

| 경로 | 대상 기기 | 역할 |
|---|---|---|
| `/` | 모바일 | 세 매장 전체 메뉴 조회·조합 저장, 매장별 설정 조회·수정, QR 포함 여부 관리와 QR 표시 |
| `/kiosk` | 노트북·키오스크 | 매장 키오스크 선택, 카메라·수동 QR 인식, 선택 매장 메뉴 ID의 카탈로그 복원, 결제 데모 |

모바일 화면의 하단 탐색은 `내 QR`, `메뉴 만들기`, `내 설정` 세 항목이다. 현재 항목은 `aria-current="page"`로 식별하며, 키오스크는 모바일 하단 탐색을 공유하지 않는 독립 화면이다.

## 3. 메뉴 선택 모델

메뉴 생성은 세 단계로 진행한다.

1. 매장: 맥도날드, 서브웨이, 스타벅스
2. 카테고리: API가 매장별로 제공하는 카테고리
3. 실제 메뉴: 안정 ID, 이름, 변형, 가격 유형, 이미지 출처, 옵션 그룹을 가진 메뉴 목록

### 3.1 카탈로그 ID와 변형

- 메뉴 ID는 QR 문법에 맞는 영문·숫자·하이픈·밑줄 문자열이며 `{storeKey}-{product}-{variant}`를 기본 형태로 사용한다.
- 공식 사이트의 숫자 ID는 변경될 수 있으므로 `sourceProductId`로 분리하고 QR의 장기 식별자로 직접 사용하지 않는다.
- 서브웨이 15cm/30cm와 스타벅스 HOT/ICED처럼 주문 결과를 결정하는 핵심 변형은 별도 메뉴 ID다.
- 메뉴명, 가격, 이미지 URL, 판매 여부, 옵션은 QR에 복제하지 않고 API 결과를 표시한다.
- 기존 숫자 맥도날드 ID는 로컬 저장 마이그레이션과 레거시 QR 해석 표에서 새 안정 ID로 대응한다.

### 3.2 선택과 저장

- 메뉴 카드는 다중 선택한다.
- `선택 메뉴` 바는 선택 개수, 총액, 목록 진입점을 제공한다.
- 목록의 `저장하기`가 현재 매장의 조합을 확정한다.
- 저장하면 `내 QR`로 돌아가 QR 문자열과 이미지가 즉시 갱신된다.
- QR 정보 영역의 매장 토글은 해당 매장 조합을 QR에 포함할지 결정한다.

### 3.3 내 설정 메뉴

- 하단 탐색의 `내 설정`은 매장별 설정 카드를 보여준다.
- 각 매장 카드는 저장 ID를 카탈로그에서 조회해 메뉴 이름, 현재 가격 유형, 개수와 합계를 표시한다.
- QR 포함 상태는 `QR 사용 중` 또는 `QR 제외`로 표시한다. 상태 변경은 QR 화면의 매장 토글에서 담당한다.
- 매장 카드의 `메뉴 바꾸기`는 해당 매장이 선택된 상태로 카테고리 단계부터 열고 새 조합을 만들 수 있도록 선택 메뉴를 모두 비운다.
- 편집 초안은 `savedIds`와 분리한다. 뒤로가기로 편집을 종료하거나 다른 하단 탭으로 이동하려 하면 저장 확인 모달을 표시한다.
- 모달의 안전한 기본 행동은 `저장하지 않음`이며 초기 포커스를 받는다. 이 행동은 초안을 버리고 기존 저장 메뉴를 그대로 유지한다.
- 초안에 메뉴가 있을 때만 모달의 `저장하기`를 사용할 수 있으며, 명시적으로 저장한 경우에만 `savedIds`와 QR을 갱신한다.
- 하단 탐색의 `메뉴 만들기`는 여러 매장 중 새 조합을 만들 수 있도록 매장 선택 단계부터 연다.
- 설정이 없는 매장은 `설정 없음`을 표시하고 메뉴 생성 흐름으로 진입할 수 있다.
- 설정 화면의 이름과 가격은 표시용 파생 데이터다. 저장소와 QR에는 기존처럼 메뉴 ID만 유지한다.

## 4. QR 데이터 계약

### 4.1 문법

```text
payload     = store-group *(";" store-group)
store-group = store-key "={" [menu-id *("," menu-id)] "}"
store-key   = 1*(ALPHA / DIGIT / "_" / "-")
menu-id     = 1*(ALPHA / DIGIT / "_" / "-")
```

예시:

```text
mcdonald={101,201,301}
mcdonald={mcdonald-big-mac,mcdonald-fries};subway={subway-egg-mayo-15cm};starbucks={starbucks-caffe-americano-hot}
```

### 4.2 serializer

- 활성화되고 저장 ID가 있는 매장을 맥도날드, 서브웨이, 스타벅스 순서로 직렬화한다.
- 한 매장의 중복 메뉴 ID는 첫 순서를 유지한 채 제거한다.
- 매장별 메뉴는 최대 20개, 전체 payload는 최대 1,200자로 제한한다.
- 포함된 매장이 없으면 빈 상태를 나타내는 `menu={}`를 만든다.
- `qrcode` 라이브러리가 문자열을 QR 이미지로 변환한다.
- QR 오류 정정 수준은 `M`, 출력 기준 폭은 720px다.

### 4.3 parser

키오스크는 `/([a-zA-Z0-9_-]+)=\{([^}]*)\}/g` 패턴으로 모든 매장 그룹을 찾는다. 각 그룹의 본문을 쉼표로 나눠 공백과 빈 값을 제거하고 `{ storeKey, menuIds[] }` 구조로 만든다. 중복 매장 그룹과 메뉴 ID는 첫 순서를 보존해 합친다.

파서는 알 수 없는 매장 키도 원문 분석 결과에는 보존한다. 키오스크는 사용자가 고른 `storeKey`에 해당하는 그룹만 API로 보내며 다른 매장 그룹은 표시·주문 목록에서 제외한다. 알 수 없는 메뉴 ID는 API의 `unknownMenuIds` 결과로 명시하고 인식된 QR 원문은 진단 경계로 유지한다.

## 5. 로컬 상태와 개인 QR

개인당 QR은 화면에서 한 개만 관리하며, 여러 매장 조합이 생기면 한 문자열 안에 매장 그룹을 합친다.

영속 상태는 브라우저 `localStorage`의 기존 `onemeal-menu-v1` 키에 저장한다. 키 이름을 유지해 기존 사용자를 마이그레이션한다.

```ts
type StoredMenu = {
  version: 2;
  stores: Partial<Record<"mcdonald" | "subway" | "starbucks", {
    savedIds: string[];
    enabled: boolean;
  }>>;
};
```

기존 `{ savedIds: number[], storeEnabled: boolean }` 값은 맥도날드 설정으로 읽고 알려진 숫자 ID를 새 안정 ID로 변환한다. 이 저장소는 기기 로컬 상태다. 사용자 계정, 서버 백업, 기기 간 동기화를 제공하지 않는다.

## 6. QR 생성·스캔 흐름

```text
모바일 메뉴 선택
  → 선택 목록 저장
  → 매장 키 + 메뉴 ID 직렬화
  → QR 이미지 생성
  → 키오스크 카메라 프레임
  → jsQR 원문 인식
  → 선택한 키오스크 매장 그룹과 메뉴 ID 파싱
  → 카탈로그 API로 ID 일괄 해석
  → 현재 메뉴명·가격 유형·옵션·미확인 ID 표시
  → 결제 데모
```

키오스크는 `navigator.mediaDevices.getUserMedia`로 카메라를 요청하고 비디오 프레임을 캔버스에 그린 뒤 `jsQR`로 읽는다. 인식에 성공하면 카메라 트랙을 중지한다. 카메라를 사용할 수 없는 환경에서는 샘플 QR 버튼으로 후속 화면을 확인한다.

## 7. 카탈로그 API 경계

키오스크 parser 결과는 다음 요청으로 변환한다.

```json
{
  "storeId": "mcdonald",
  "menuIds": ["mcdonald-big-mac", "mcdonald-fries"]
}
```

`POST /v1/catalog/resolve`는 매장 키와 메뉴 ID를 검증하고 현재 이름, 가격 유형, 판매 여부, 변형, 옵션 정보를 반환한다. 다른 매장 또는 없는 ID는 `unknownMenuIds`에 넣어 부분 성공을 허용한다. 프런트엔드는 QR에 들어 있지 않은 가격이나 이름을 추측하지 않고 응답 데이터를 주문 목록에 표시한다.

API 연결 전후의 계약 경계는 다음과 같다.

- QR: 매장 키와 메뉴 ID만 전달
- 키오스크 프런트엔드: 원문 보존, 문법 파싱, API 요청 구성
- 백엔드 카탈로그: ID 유효성, 매장 소속, 가격 유형·판매 상태·옵션의 진실 원천
- 결제 시스템: 검증된 주문과 금액을 받아 별도 처리

## 8. PWA와 배포

- Web App Manifest: `/manifest.webmanifest`
- Service Worker: `/sw.js`
- 시작 경로와 scope: `/`
- 표시 모드: `standalone`
- 기본 방향: `portrait`
- Sites 프로젝트 연결: `.openai/hosting.json`

카메라 접근은 보안 컨텍스트가 필요하므로 프로덕션에서는 HTTPS를 사용한다. 서비스 워커는 앱 셸과 필수 정적 자산을 캐시하지만, 장래의 메뉴 API 응답은 데이터 신선도 정책이 정해지기 전까지 무조건 캐시하지 않는다.

## 9. 접근성·UX 원칙

- 큰 글자, 높은 대비, 충분한 터치 영역을 우선한다.
- 한 화면의 핵심 행동을 하나로 제한하고 선택 단계 진행 상태를 보여준다.
- 색상만으로 선택 여부를 표현하지 않고 체크 표시와 `aria-pressed`를 사용한다.
- 매장 토글은 `role="switch"`와 상태 레이블을 제공한다.
- 하단 탐색은 텍스트와 아이콘을 함께 제공하고 현재 화면을 `aria-current`로 표시한다.
- 설정 화면은 QR 상태를 텍스트 배지로 제공하고 매장별 메뉴를 구조화된 목록으로 표시한다.
- 카메라 오류 시 권한 확인 안내와 카메라 없는 대체 흐름을 제공한다.
- 불필요한 설명을 줄이되 결과, 가격, 선택 개수, 저장 성공처럼 다음 행동에 필요한 정보는 숨기지 않는다.

## 10. 개인정보·보안

- v0.1.0은 이름, 이메일, 결제 정보 같은 개인정보를 수집하거나 저장하지 않는다.
- 메뉴 조합은 현재 기기의 브라우저 저장소에만 존재한다.
- QR은 비밀 토큰이 아니며 카메라에 보이는 누구나 내용을 읽을 수 있다.
- QR의 메뉴 ID는 주문 의사 표현일 뿐 가격·재고·결제 권한을 증명하지 않는다.
- 백엔드 연결 시 입력 길이, 허용 매장 키, 메뉴 ID 형식과 개수를 서버에서 다시 검증해야 한다.

## 11. 수용 기준

- `Prepped`가 모바일, 키오스크, PWA, 검색·공유 metadata에 일관되게 표시된다.
- 모바일에서 메뉴 저장 후 QR이 갱신된다.
- 모바일에서 `내 설정`을 열어 매장별 저장 메뉴와 QR 포함 상태를 확인하고 메뉴 생성 흐름으로 수정할 수 있다.
- 모바일이 세 매장 전체 메뉴를 API로 조회하고 매장별 설정을 한 QR로 만든다.
- 키오스크가 매장을 선택하고 카메라 또는 수동 코드에서 해당 그룹만 읽어 카탈로그 메뉴를 표시한다.
- QR 문자열 문법과 브라우저 로컬 저장 경계가 코드와 문서에서 일치한다.
- `/`와 `/kiosk`가 프로덕션에서 모두 제공된다.
- `npm run build`가 성공한다.
